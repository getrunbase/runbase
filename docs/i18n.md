# i18n: English and French

The whole UI exists in `en` and `fr`. No visible text is hard-coded.

## Architecture

- Library: `next-intl`, server rendering.
- Language (`apps/web/i18n/request.ts`): middleware header (public URL) > `NEXT_LOCALE` cookie > `Accept-Language` > `en`.
- The app has no URL prefix. Language switch: user menu (`components/locale-menu.tsx`, server action `i18n/actions.ts`).
- No public page: the self-hosted app only has a sign-in wall (`/` without a session redirects to `/login`). Everything is `noindex` (root layout) and `app/robots.ts` disallows everything. The language follows the cookie, then `Accept-Language`, without a URL prefix.

## Messages

- One file per namespace and per language: `apps/web/messages/<en|fr>/<ns>.json`. List of namespaces: `i18n/config.ts` and `global.d.ts`.
- `en` is the source of truth for types: a missing key breaks `pnpm typecheck`.
- `messages.test.ts` fails if `fr` and `en` do not have the same keys or if a value is empty.
- `common`: shared words (Save, Cancel…). Reuse them before creating a key.
- Short keys, grouped by screen: `objects.table.empty`. No sentence as a key.
- Plurals and variables: ICU (`"{count, plural, one {# record} other {# records}}"`).

## Writing a component

- Server component: `const t = await getTranslations("ns")`.
- Client component: `const t = useTranslations("ns")`.
- Dates and numbers: `useFormatter()` / `getFormatter()`, never a hard-coded `"fr-FR"`.
- Pure functions (lib): return keys, translate at render time.
- Content entered by the user (database names, records) is not translated.
- MCP tool names, code and identifiers are not translated: `{"objects.create"}`.

## Page titles

- Every `page.tsx` exports `generateMetadata`, usually `export const generateMetadata = pageTitle("key")` (`lib/page-title.ts`), with the key in `common.titles` (en and fr). Pages that need a dynamic title write their own `generateMetadata` with `getTranslations`.
- The root layout sets `title.template` (`"%s · Runbase"`) and the default title.

## Pages outside the app shell

- Sign-in, sign-up, password reset, invitations and OAuth consent render inside `AuthShell`, which shows `LocaleSwitch` (`components/locale-switch.tsx`): same `NEXT_LOCALE` cookie and server action as the user menu. Without it, a visitor whose browser sends `Accept-Language: fr` cannot get the English UI before signing in.

## Guardrails

- `pnpm lint` (`no-restricted-syntax`) rejects hard-coded JSX text, hard-coded `placeholder`/`title`/`alt`/`label`/`aria-label` attributes and hard-coded locales. It applies to every `apps/web/app/**/*.tsx` and `apps/web/components/**/*.tsx` file, auth pages included (`components/ui` and `app/api` excluded).
- `lib/page-titles.test.ts` fails if a `page.tsx` has no `generateMetadata` or uses a `common.titles` key missing in a locale.
- Adding a language: add it to `locales`, create `messages/<l>/`; the parity test lists what is missing.

## Errors and the core

The core (`packages/core`), the MCP server (`app/api/mcp`) and the worker are English only. Text meant for agents (tool descriptions, guides, examples, recipes) is never translated. Text shown in the UI carries a stable code that the web app translates.

### Core side

```ts
import {
  appError,
  errorItem,
  notFound,
  requireConfirm,
} from "@getrunbase/core/errors";
// (client: `@getrunbase/core/app-error`, no server dependency)

throw appError("records.notFound", "Record {id} not found", { id });
throw notFound(
  "functions.notFound",
  "Function {name} not found. See functions.list.",
  { name },
); // kind not_found
requireConfirm(confirm, "overview.purgeConfirm", "Test data purge"); // kind confirm_required
throw appError(
  "functions.alreadyExists",
  "Function {name} already exists.",
  { name },
  { kind: "conflict" },
);
```

- `AppError`: `code` (translation), `params`, `message` (rendered English), `kind` (machine category for MCP: `[not_found] …`), `items` (details).
- Code: `domain.camelName`, a literal as the first argument (the test reads it from the source).
- Subclasses (`QuotaError`, `HttpError`, `FunctionError`, `CostCapExceeded`): optional last argument `{ code, params }`. `InvalidWorkflow`, `InvalidPage`, `CompileFailed` and `RunAlreadyActive` have a fixed code.
- Lists (workflow validation): `errorItem(code, template, params)` -> `{ code, params, message }`. `new InvalidWorkflow(items)` accepts items and strings (backward compatibility, untranslated `error` code).
- Dry run: `DryRunStep.reasonItem = errorItem(...)`, `reason` keeps the English message.

### Web side

- Translations: `messages/fr/errors/{data,automation,interfaces,platform}.json`, flat keys (`"records.notFound": "Fiche {id} introuvable"`), simple `{param}` template. No `en` file: English is the core message.
- Domains: `data` (records, objects, databases, query, events, webhooks, ingest, files, views, filter), `automation` (workflows, runs, blocks, functions, triggers, secrets), `interfaces` (pages, components), `platform` (auth, api-keys, members, workspaces, quotas, audit, errors, overview, feedback, email).
- Display: `errorText(e, locale)` (`lib/error-text.ts`), `useErrorText()` on the client, `await getErrorText()` on the server (`lib/error-text-server.ts`). Accepts an error, an item `{ code, params, message }` or a string. Unknown code: English message.
- Server actions: `return { error: actionError(e) }` (`lib/action-error.ts`, type `ActionError`), then `errorText(state.error)` at render time. Examples: `app/functions/actions.ts` + `test-panel.tsx`, `app/databases/actions.ts` + `objects/schema-editor.tsx`.
- Guardrail: `lib/error-codes.test.ts` fails if a literal code (`appError`, `errorItem`, `notFound`, `requireConfirm`) of the core or the web app has no translation, or if a translation is no longer used. The MCP server is excluded (errors seen by agents only).

### Building block labels

`blocksService.list()` (`packages/core/src/blocks/index.ts`) exposes `label` and `description` in English. The web app translates them through `messages/{en,fr}/workflows.json` under `blocks.<type>.label` and `blocks.<type>.description`, falling back to the core text when the key is missing (`t.has(key) ? t(key) : b.label`). User functions exposed as blocks keep their name (user content).

## Documentation site (apps/docs)

The docs site uses the official Fumadocs i18n (`defineI18n`, `lib/i18n.ts`), not next-intl: its UI is a few static, server-rendered texts, and Fumadocs already handles per-language content, page trees, search indexes and the language switcher.

### URLs

- English is the default and has no prefix: `/docs/quickstart`. French lives under `/docs/fr/quickstart`. Existing English URLs did not change.
- `/docs/en/...` redirects (308) to `/docs/...`. The home page is `/` (English) and `/fr` (French).
- Pages render under `app/[lang]/`. `proxy.ts` rewrites the public URL to the internal path (`/docs/fr/x` -> `/fr/docs/x`). The routing rules are in `lib/locale-path.mjs`, with tests.

### Content: one English page = one French page at the same path

- `content/docs/en/<path>.mdx` is the source. Its translation is `content/docs/fr/<path>.mdx`, with the same file name and folder (Fumadocs parser `dir`).
- A folder title (`meta.json` with `"title"`) is translated in `content/docs/fr/<folder>/meta.json`. Keep the same `pages` list.
- A missing French page falls back to the English page (`fallbackLanguage: "en"`). The French UI shows the English content at `/docs/fr/<path>`, with the English URL as canonical. There is no `hreflang="fr"` and no French sitemap entry until the translation exists.
- Links: keep the English URLs (`/docs/concepts#data`). A French page renders them as `/docs/fr/...` (`localizeHref`). Anchors follow the French headings: `## Démarrer` -> `#démarrer`. `lib/links.test.mjs` checks the links of every language.
- Do not translate code, MCP tool names, identifiers, CLI commands or JSON keys.
- Pages generated from the code (`scripts/gen-docs.mts`: REST API, MCP tools, nodes, self-hosting) are generated in English and French by `pnpm gen:docs`. The fixed prose of the templates (titles, intros, table headers) lives in `apps/docs/messages/{en,fr}/generated.json`. The texts that come from the code (tool, node and endpoint descriptions) stay English in the code; their French version lives in `apps/docs/translations/fr/generated.json`, as `{ "<stable id>": { "en": "<current English text>", "fr": "..." } }`. The French self-hosting page is `apps/docs/translations/fr/self-hosting.md`, whose first line records the SHA-256 of `docs/self-hosting.md`. `pnpm gen:docs` fails and lists every missing or stale id (English text changed since the translation); run it with `GEN_DOCS_MISSING=missing.json` to get those entries in a file, translate them, and add them to `generated.json`.

### Parity test (blocking)

`lib/translations.test.mjs` (`pnpm --filter @getrunbase/docs test`) fails when:

- an English page has no French page and is not listed in `lib/translations-pending.json`;
- a pending entry is already translated (remove it from the list);
- a French file has no English source (orphan).

When you add an English page, add its French page in the same pull request. If that is not possible, add its path to `translations-pending.json`. When you translate a page, remove it from that list.

### UI texts

- Site texts (home, metadata, breadcrumb, llms.txt): `apps/docs/messages/<en|fr>/site.json`, read through `lib/messages.ts`. A missing key breaks `pnpm typecheck` (`satisfies`), and `lib/messages.test.mjs` checks the keys and empty values.
- Fumadocs UI texts (search, table of contents, pagination...): English by default, French in `apps/docs/messages/fr/fumadocs.json` (keys from `fumadocs-ui`).
- The same ESLint rule as the web app rejects hard-coded JSX text in `apps/docs/app`, `components` and `lib` (`.tsx`).

### SEO per language

- `hreflang` for every existing language, plus `x-default` (English), and a canonical URL per language (`lib/seo.ts`).
- The multilingual sitemap (`/docs/sitemap.xml`) lists one entry per page and per real language, with `xhtml:link` alternates.
- `llms.txt` exists per language: `/docs/llms.txt` and `/docs/fr/llms.txt`.
- Each page has JSON-LD (`TechArticle` + `BreadcrumbList`) and an OG image (`/docs/og/<lang>/<path>/image.png`).

### Adding a language

Add it to `LANGUAGES` (`lib/locale-path.mjs`) and to the `Lang` type (`lib/i18n.ts`). Then create `messages/<l>/site.json` and `messages/<l>/fumadocs.json`, and `content/docs/<l>/`. The parity test lists the pages to translate. Extend it to the new language.
