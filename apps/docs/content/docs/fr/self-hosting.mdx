Exécutez Runbase sur votre propre serveur avec Docker, à partir d'images
prêtes à l'emploi. Objectif : une instance opérationnelle en moins de 5 minutes.

## Prérequis

- Docker Engine 24+ avec le plugin Compose (`docker compose version`).
- `openssl` (utilisé par `setup.sh` pour générer les secrets).
- 2 Go de RAM. Les images existent pour `linux/amd64` et `linux/arm64`.

## Démarrage rapide

```sh
git clone https://github.com/getrunbase/runbase runbase && cd runbase
./setup.sh https://runbase.example.com   # ou ./setup.sh pour http://localhost:3000
docker compose -f docker-compose.selfhost.yml up -d --wait
docker compose -f docker-compose.selfhost.yml exec worker pnpm admin:create you@example.com
```

Ouvrez `<votre URL>/login` et demandez un lien de connexion. Sans configuration
e-mail, le lien n'est pas envoyé : il est affiché dans les journaux du service web.

```sh
docker compose -f docker-compose.selfhost.yml logs web | grep email:console
```

`setup.sh` copie `.env.example` vers `.env` (mode 600) et génère
`BETTER_AUTH_SECRET`, `SECRETS_MASTER_KEY`, `POSTGRES_PASSWORD`,
`QUERY_DB_PASSWORD`, `REDIS_PASSWORD` et `SANDBOX_TOKEN`. Il n'écrase jamais un
`.env` existant (`--force` régénère tout, ce qui rend les secrets stockés
illisibles). Le fichier compose refuse de démarrer tant qu'un secret manque.

## Ce qui tourne

| Service    | Rôle                                                                                               | Réseau                    |
| ---------- | -------------------------------------------------------------------------------------------------- | ------------------------- |
| `postgres` | Base de données (volume `postgres-data`)                                                           | internal                  |
| `redis`    | Files d'attente et pub/sub, protégé par mot de passe (volume `redis-data`)                         | internal                  |
| `migrate`  | Ponctuel : applique les migrations de la base avant le démarrage des applications                  | internal                  |
| `worker`   | Exécute les workflows, les déclencheurs et les planifications                                      | internal, egress, sandbox |
| `web`      | Application Next.js, port 3000 dans le conteneur                                                   | internal, egress, sandbox |
| `sandbox`  | Exécute le code des fonctions (Deno), sans root, en lecture seule, sans accès à la base ni à Redis | sandbox, sandbox-egress   |
| `renderer` | Chromium headless pour les captures de pages et les audits d'accessibilité                         | internal                  |

Le réseau `internal` n'a ni accès à internet ni port publié : seule
l'application web est joignable depuis l'hôte, sur `127.0.0.1:${WEB_PORT}` par
défaut. Les fichiers téléversés sont stockés sur le disque local dans le volume
`files-data`, partagé par web, worker et renderer. Le service `sandbox` accède
à internet via `sandbox-egress` mais jamais au réseau `internal`.

## Configuration

Chaque paramètre est documenté dans `.env.example`, valeurs obligatoires en
premier. Les paramètres facultatifs les plus courants :

- **E-mail.** Resend (`RESEND_API_KEY`) ou n'importe quel serveur SMTP
  (`SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_SECURE`).
  `EMAIL_FROM` est obligatoire dès qu'un fournisseur est configuré. Sans l'un
  ni l'autre, les e-mails sont affichés dans les journaux du service web (mode
  console).
- **Méthode de connexion.** `AUTH_METHOD=magic-link` (par défaut) : lien sans
  mot de passe envoyé par e-mail. `AUTH_METHOD=password` : e-mail et mot de
  passe (8 caractères minimum), avec une page d'inscription sur `/signup` et une
  réinitialisation du mot de passe par e-mail sur `/reset-password` lorsque
  Resend ou SMTP est configuré. Lu à l'exécution : redémarrez le conteneur
  `web`, sans reconstruire l'image. Les comptes créés sans mot de passe
  (invitations, lien magique) en définissent un via le lien de réinitialisation.
- **Inscriptions.** Fermées par défaut ; définissez `SIGNUPS_ENABLED=true` pour
  les ouvrir, ou créez les comptes avec `pnpm admin:create` comme ci-dessus.
- **Connexion avec Google.** Définissez `OAUTH_GOOGLE_CLIENT_ID` et
  `OAUTH_GOOGLE_CLIENT_SECRET` (le même client OAuth Google que les connecteurs
  Google) pour afficher un bouton « Continuer avec Google » sur les pages de
  connexion et d'inscription. Voir [Connexion avec Google](#connexion-avec-google).
- **Blocs d'IA.** Aucune clé fournie par la plateforme : chaque espace de
  travail ajoute sa propre clé de fournisseur en tant que secret (Paramètres ›
  Secrets), et chaque bloc d'IA et chaque page indique le fournisseur, le modèle
  et le secret qu'il utilise.
- **Runtime des composants de code.** `NEXT_PUBLIC_RUNTIME_ORIGIN` sert l'iframe
  isolée des composants de code depuis un second domaine pointant vers le même
  conteneur web (par exemple `https://runtime.example.com`). Cette valeur est
  figée au moment du build : l'image publiée est livrée avec une valeur vide
  (même origine, l'iframe reste isolée). Pour utiliser une origine dédiée,
  construisez l'image web avec
  `docker build --build-arg NEXT_PUBLIC_RUNTIME_ORIGIN=https://runtime.example.com .`
  et reconstruisez-la à chaque changement.
- **Google (Gmail, Calendar, Sheets, Drive).** `OAUTH_GOOGLE_CLIENT_ID` et
  `OAUTH_GOOGLE_CLIENT_SECRET` : client OAuth du connecteur Google. Étapes et
  scopes : [Connecter Google](/docs/guides/google).
- **Version.** `RUNBASE_VERSION` fixe un tag d'image (`latest` par défaut).

Appliquez un changement avec `docker compose -f docker-compose.selfhost.yml up -d`.

### Télémétrie anonyme

La télémétrie anonyme est activée par défaut. Le worker envoie un ping par jour
au récepteur du projet, afin que le projet puisse mesurer l'adoption en
auto-hébergement. `RUNBASE_TELEMETRY_URL` le redirige vers un autre récepteur.
Au démarrage, le worker indique dans ses journaux si la télémétrie est activée
et comment la désactiver.

Champs envoyés, en `POST` JSON, et rien d'autre :

| Champ        | Exemple        | Signification                                                                                                                     |
| ------------ | -------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `instanceId` | `5b0c…-…`      | UUID aléatoire tiré au premier démarrage, stocké dans Redis. Non dérivé de données de l'hôte, des utilisateurs ou des locataires. |
| `version`    | `1.4.0`        | `APP_VERSION` de l'image (`dev` si non définie).                                                                                  |
| `os`, `arch` | `linux`, `x64` | Plateforme du processus worker.                                                                                                   |
| `node`       | `22.11.0`      | Version de Node.js.                                                                                                               |
| `workspaces` | `<10`          | Nombre d'espaces de travail, par tranche (`0`, `<10`, `<100`, `<1000`, `<10000`, `<100000`, `100000+`).                           |
| `workflows`  | `<100`         | Nombre de workflows, mêmes tranches.                                                                                              |
| `runs`       | `<10000`       | Nombre d'exécutions de workflows conservées, mêmes tranches.                                                                      |

Aucune donnée personnelle : ni noms, ni e-mails, ni données dérivées de l'IP,
ni contenu des locataires. Un ping en échec (réseau, récepteur indisponible)
est ignoré et n'affecte jamais l'application.

**Désactivation :** définissez `RUNBASE_TELEMETRY=0` dans `.env`, puis
appliquez le changement. Le worker n'envoie alors plus aucune requête.

## Connexion avec Google

Un seul client OAuth Google sert à la fois à la connexion et aux connecteurs
Google.

1. Dans la console Google Cloud, créez (ou réutilisez) un client OAuth de type
   « Application Web ».
2. Ajoutez l'URI de redirection autorisée
   `<BETTER_AUTH_URL>/api/auth/callback/google` (par exemple
   `https://runbase.example.com/api/auth/callback/google`), à côté de l'URI de
   redirection des connecteurs si vous en utilisez déjà une.
3. Définissez `OAUTH_GOOGLE_CLIENT_ID` et `OAUTH_GOOGLE_CLIENT_SECRET`, puis
   redémarrez le conteneur `web`.

La connexion ne demande que `openid`, `email` et `profile` : ces scopes ne sont
pas sensibles, l'écran de consentement ne nécessite donc aucune validation par
Google. Un compte Google dont l'e-mail vérifié correspond à un compte existant y
est rattaché, sans doublon. Avec les inscriptions fermées (`SIGNUPS_ENABLED` non
défini), la connexion avec Google ne fonctionne que pour les comptes existants
et les membres invités.

## Reverse proxy (HTTPS)

Gardez `WEB_BIND=127.0.0.1` (par défaut) et placez un reverse proxy devant.
`BETTER_AUTH_URL` doit être l'URL https publique.

Caddy (certificats automatiques) :

```caddyfile
runbase.example.com {
  reverse_proxy 127.0.0.1:3000
}
```

nginx :

```nginx
server {
  listen 443 ssl;
  server_name runbase.example.com;
  # ssl_certificate ... (certbot)
  client_max_body_size 20m;
  location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_buffering off;   # réponses en streaming
  }
}
```

## Sauvegardes

Sauvegardez trois éléments :

1. **`.env`**, surtout `SECRETS_MASTER_KEY` : sans elle, les secrets stockés
   dans la base ne peuvent pas être déchiffrés.
2. **La base de données** :

   ```sh
   docker compose -f docker-compose.selfhost.yml exec -T postgres \
     sh -c 'pg_dump -Fc -U "$POSTGRES_USER" "$POSTGRES_DB"' > runbase-$(date +%F).dump
   ```

3. **Les fichiers téléversés** (volume `files-data`) :

   ```sh
   docker run --rm -v runbase_files-data:/data -v "$PWD":/out alpine \
     tar czf /out/files-$(date +%F).tgz -C /data .
   ```

   Le nom du volume est préfixé par le nom du projet compose (le nom du
   dossier par défaut) : vérifiez-le avec `docker volume ls`.

Restaurer une sauvegarde de la base dans une nouvelle stack :

```sh
docker compose -f docker-compose.selfhost.yml stop web worker
docker compose -f docker-compose.selfhost.yml exec -T postgres \
  sh -c 'pg_restore --clean --if-exists -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < runbase-YYYY-MM-DD.dump
docker compose -f docker-compose.selfhost.yml up -d
```

Redis ne contient que des files d'attente et un état transitoire ; la base de
données fait foi.

## Durcissement

Ce que la stack fait déjà :

- Postgres et Redis sont sur un réseau interne sans port exposé sur l'hôte ;
  Redis exige un mot de passe.
- Les images `web`, `worker`, `renderer` et `sandbox` tournent avec
  l'utilisateur non root `node` (uid 1000). Le service ponctuel `files-perms`
  rend à `node` les fichiers d'un volume `files-data` créé par une ancienne
  image qui tournait en root.
- Le code des fonctions s'exécute dans le service `sandbox` : système de
  fichiers en lecture seule, aucune capability, aucun accès à Postgres ni à
  Redis, plages d'adresses privées refusées.

Sur l'hôte, nous recommandons :

- SSH par clés uniquement (`PasswordAuthentication no`, `PermitRootLogin no`),
  fail2ban, mises à jour de sécurité automatiques.
- Un pare-feu qui n'autorise que SSH, 80 et 443. Docker contourne `ufw` pour
  les ports publiés : ne publiez que le reverse proxy (gardez
  `WEB_BIND=127.0.0.1`).
- La rotation des journaux Docker dans `/etc/docker/daemon.json`
  (`"log-opts": {"max-size": "10m", "max-file": "3"}`) et `"live-restore": true`.
- Pour filtrer aussi la sandbox au niveau réseau, ajoutez des règles iptables
  `DOCKER-USER` qui rejettent le trafic du bridge `sandbox-egress` vers les
  plages privées (10/8, 172.16/12, 192.168/16, 127/8, 169.254/16, 100.64/10,
  fc00::/7, fe80::/10) et vers l'IP publique de l'hôte.
- Pour une restauration à un instant donné au-delà des sauvegardes nocturnes,
  archivez le WAL de Postgres vers un stockage objet avec un outil comme wal-g
  ou pgBackRest, et testez régulièrement une restauration.

## Mises à jour

```sh
git pull                                   # changements du fichier compose et de .env.example
docker compose -f docker-compose.selfhost.yml pull
docker compose -f docker-compose.selfhost.yml up -d --wait
```

Le service `migrate` applique les migrations de la base avant le démarrage du
worker et de l'application web. Sauvegardez d'abord la base de données. Pour
rester sur une version donnée, définissez `RUNBASE_VERSION` dans `.env` ; pour
revenir en arrière, indiquez le tag précédent et restaurez la sauvegarde faite
avant la mise à jour.

## Dépannage

- `required variable ... is missing a value: run ./setup.sh` : il manque un
  secret dans `.env` ; lancez `./setup.sh` (ou ajoutez la valeur).
- `docker compose -f docker-compose.selfhost.yml ps` affiche l'état de santé de
  chaque service ; `logs worker` affiche les erreurs de migration.
- `EMAIL_FROM is required when an email provider (...) is configured` :
  définissez `EMAIL_FROM` avec un expéditeur vérifié par votre fournisseur.
